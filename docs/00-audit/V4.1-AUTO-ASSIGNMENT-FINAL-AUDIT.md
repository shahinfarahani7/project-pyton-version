# EdgeMint v5.0 Automatic Assignment Final Audit

## Audit decision

**Passed for execution-package design and autonomous Cursor implementation.**

EdgeMint v5.0 contains no per-task Worker Accept, Reject, confirmation, offer or consent step. Current policy consent plus account-wide `Available` status is the only participation opt-in. Once the Router selects a compatible device, PostgreSQL creates the assignment and exclusive lease directly. The Worker Agent acknowledges delivery only at the transport layer and automatically starts after validating the signature, lease token, fencing token, model digest, input digest and local resources.

This decision does not claim that a live production deployment is certified. The target organization must still provide the external release evidence required by `production/RELEASE-INPUTS.yaml` and `production/EXTERNAL-EVIDENCE-CONTRACT.md`; the production gate remains fail-closed.

## Final normative flow

1. Admission creates an immutable task revision with server-derived execution requirements.
2. PostgreSQL queue selection expires overdue or reassignment-exhausted attempts, applies hard starvation protection, workspace deficit fairness, server-authoritative priority, deadline ordering and a deterministic tie-break.
3. A Router instance obtains a short-lived claim on exactly one attempt.
4. Candidate Workers are filtered and scored deterministically.
5. `AcquireAssignmentLease` revalidates all critical facts atomically at commit time: claim ownership, reassignment budget, Available status, effective schedule, Worker/device lifecycle, attestation, trust, consent, heartbeat freshness, battery, thermal state, network policy, charging policy, device tier, runtime ABI, RAM, storage, region, exact model digest and device capacity.
6. The same transaction reserves capacity, allocates a monotonic fence token, creates the assignment in `leased`, changes the attempt from `matching` to `leased`, clears the queue claim and inserts outbox events.
7. WebSocket delivery is targeted. ACK means receipt only. `GET /assignments:next` is a pull fallback for the already-created lease; it never creates or returns an offer.
8. The automatic-start deadline is the delivery deadline plus the start grace. The Agent reports `started` using a monotonic sequence and then executes.
9. Machine-only unavailability is accepted only when the latest persisted health snapshot proves the selected reason. A mismatched reason changes no state and creates no reassignment.
10. Lease expiry, start timeout or validated unavailability requeues or terminates the attempt according to policy and allocates a higher fence on reassignment. Stale results are evidence-only and never earn a reward.
11. Reassignment-budget exhaustion terminally expires the attempt and hands control to retry policy or policy-controlled Cloud fallback; the attempt cannot spin indefinitely in `matching`.
12. Changing the Worker to `Unavailable` affects future leases only. It never cancels, rejects or revokes an already leased or running assignment.

## Gaps found and closed in this audit

- Removed assignment `offered`, `accepted` and `rejected` states, APIs, events, UX actions and timeouts.
- Replaced assignment Accept/Reject operations with automatic `started` and machine-only `unavailable` reports.
- Defined deterministic queue order, workspace fairness, hard starvation bound, priority authority and exact feature-normalization formulas.
- Added SQL-persisted queue claims and fairness state to prevent two Router instances from selecting the same attempt.
- Added exact claim expiry and lifecycle outbox evidence for deadline expiry.
- Added reassignment-budget termination so exhausted attempts cannot remain in the queue forever.
- Added account-wide Available status, explicit schedule mode and effective UTC availability window.
- Defined that availability changes apply only to future assignments.
- Added immutable task-revision requirements for tier, runtime ABI, free RAM, free storage and allowed Worker regions.
- Added device region, current heartbeat resource facts and verified model-install state to the atomic lease gate.
- Revalidated every critical eligibility and capacity condition in the same PostgreSQL transaction that creates the lease.
- Corrected the automatic-start deadline so the delivery window and start grace are sequential.
- Correlated unavailable reason codes with the latest persisted health snapshot and immutable revision requirements, preventing `unavailable` from acting as a hidden Reject action.
- Added idempotent start, unavailable and renewal sequences, start/renewal timeout recovery and stale-fence behavior.
- Aligned use cases, scenarios, operation contracts and SQL outbox events for start, unavailable and renewal commands.
- Removed stale AssignmentOffer terminology from the executive implementation contract, product domain chain, implementation backlog, acceptance plan, SRE runbook, ownership matrix and Cursor work packages.
- Added a fail-closed v4.0-to-v5.0 PostgreSQL migration for legacy offered/accepted rows.
- Synchronized package, portal, Worker, Helm, API contract and release versions to 5.0.0.

## Environment-dependent checks

The Python source compiled successfully in the audit environment and the included backend test suite completed with 27 passing tests. The environment provided Python 3.13.5 rather than the pinned Python 3.13.14 runtime.

The audit container did not provide a live PostgreSQL 18.4 server, `psql`, Docker, Terraform, Helm, Kubernetes, AWS, Stripe, signing keys, physical devices or organizational approval identities. Terraform controls passed repository validation, but full HCL parsing emitted an explicit warning because `python-hcl2` was unavailable. No unavailable build, migration, cloud, security, load, backup/restore or production evidence was fabricated.

The package supplies deterministic commands and evidence contracts for those checks, and the production gate rejects missing or placeholder evidence.

## Final conclusion

The automatic-assignment design is explicit, deterministic and fail-closed. A Worker gives consent once by maintaining current policy consent and enabling Available mode. No task-by-task confirmation exists. Internal specification and execution-package gaps identified during this audit are closed; live deployment certification remains conditional on genuine external evidence.
