# سناریوی بار مدیر تسک

شبیه‌سازی قطعی، بدون دیتابیس. رتبه‌بندی همان `RouterService.rank_workers` است. تخصیص زندهٔ پایگاه داده را عوض نمی‌کند.

## فرض

- ۱۰۰ دستگاه آماده‌اند: ۴۰ تا T1، ۳۰ تا T2، ۲۰ تا T3، ۱۰ تا T4.
- ۵۰۰ تسک یک‌جا می‌رسند: ۲۵۰ سبک (`system`)، ۱۵۰ تشخیص متن (`paddle_ocr`)، ۷۰ مدل زبانی (`mediapipe_llm`)، ۳۰ مدل بینایی (`vlm_runtime`).
- دستگاه قوی‌تر CPU و RAM بیشتری دارد. بودجه با حالت مشارکت ۵۰٪ و ذخیرهٔ ایمنی سیاست فعلی حساب می‌شود.
- تسک سنگین یعنی حداقل سطح دستگاهش T3 یا T4 باشد.

## قواعد

- سطح ناکافی، بودجهٔ CPU یا RAM یا فضای ذخیره‌سازی، و سقف همزمانی سطح (T4 دو اجاره، بقیه یکی) همان فیلترهای فعلی‌اند.
- سقف اضافهٔ این سناریو: RAM رزروشده از ۷۰٪ کل RAM دستگاه بیشتر نشود، و هر دستگاه هم‌زمان فقط یک تسک سنگین داشته باشد.
- بین دستگاه‌های هم‌امتیاز، تسک سنگین به سطح قوی‌تر می‌رود. امتیاز بالاتر را سطح قوی‌تر پس نمی‌زند.
- تسکی که روی هیچ دستگاهی جا نشود در صف می‌ماند. هیچ تسکی حذف نمی‌شود.

## قبول بودن

سناریو رد می‌شود اگر دستگاهی از بودجه یا سقف همزمانی یا ۷۰٪ RAM بگذرد، دو تسک سنگین روی یک دستگاه باشد، تسک سنگین در امتیاز مساوی به سطح ضعیف‌تر برود، یا تعداد صف به‌علاوهٔ تخصیص ۵۰۰ نباشد. در پایان، هر تسک صف‌شده دوباره با وضعیت نهایی دستگاه‌ها سنجیده می‌شود و هنوز نباید جا داشته باشد.
